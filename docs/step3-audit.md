## Представительные профили

C/G/R/H/F/E/A приведены в таком порядке. ΔC и ΔG — сырые сокращения
критического и общего дефицита, а не нормализованные факторы. Все альтернативы
моделируются отдельно от одной базы; готовность — покрытие требований цели.
В истории n = число учтённых записей, w = суммарный вес, +/− = вес положительных
и отрицательных исходов, NS/C = недавние похожие no_show/completed, rating/score =
количество наблюдений для F. «Недавние похожие» означает возраст ≤365 дней
и similarity≥0,5; эти пороги влияют только на счётчики доказательств.

## Производительность

Замеры `perf_counter`, Python 3.9, локальное выполнение с уже загруженными
данными; чтение файлов и сеть в измерения не входят.

- E0001, 20 повторов: медиана **8.80 мс**, максимум **9.18 мс**.
- Все 200 сотрудников последовательно: **1776.69 мс**.
- Цель обычного UI/API-ответа из исходного задания — <2000 мс. Сам расчёт для
  одного сотрудника укладывается с большим запасом; API и сеть ещё не измерялись.

## Ограничения и принятые решения

- Score сравнивает события внутри конкретного пула кандидатов. Нормализаторы
  различаются между сотрудниками; оценка не является вероятностью повышения
  и не подходит как универсальная метрика сравнения сотрудников.
- При отсутствии критического эффекта вес 0,35 остаётся неиспользованным.
  Максимально возможная оценка в таком пуле — 0,65. Это утверждённая политика.
- H/F сглажены prior 0,5 с весом 2. Общий потолок вклада истории — 0,15;
  влияние слабой или малопохожей истории остаётся близким к нейтральному.
- Реальные assigned_by: self/manager/hr (865/497/1381 записей). Обязательность
  определяется событием, а не источником назначения. Неизвестный источник
  получает вес 0,5 и диагностический счётчик, без исключения кандидата.
- Некорректная длительность, включая непредставимую конечным числом эффективность
  при крайне малом значении, даёт E=0 и последнее место по длительности при
  прочих равных. Неверные необязательные rating/score пропускаются и считаются;
  отсутствующие значения не становятся нулём.
- Точная дата завершения отсутствует в CSV. Для completed_at используется
  переданное значение; иначе сохраняется дата-заменитель и диагностический
  счётчик. История до last_review_date остаётся сигналом предпочтений.
- Детальные preference-записи включаются только явно. Прежние контракты
  CareerState/eligibility сохраняют ID участий и изменения навыков. Адаптер
  backend должен выбирать поля для frontend, а не отправлять все доказательства
  как публичную модель без преобразования.
- Ограничения каталога и 27 пустых результатов с целью сохранены. Алгоритм не
  строит цепочки подготовительных курсов и не ослабляет допуск.
