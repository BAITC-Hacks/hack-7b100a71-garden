# Supabase / PostgreSQL

Frontend обращается к FastAPI. Backend подключается к PostgreSQL через `psycopg`; `DATABASE_URL` хранится только на сервере. Текущие HR/employee bearer-токены продолжают определять доступ к API. Supabase Auth в эту интеграцию не входит.

## Настройка

1. Создайте проект Supabase и откройте **Connect → Session pooler**. Этот вариант работает в сетях IPv4. Direct connection подходит, когда сервер имеет IPv6. [Документация подключений](https://supabase.com/docs/guides/database/connecting-to-postgres).
2. Скопируйте PostgreSQL URI в `.env` как `DATABASE_URL`, замените пароль базы, добавьте `sslmode=require`. Пароль с `@`, `:`, `/`, `#`, `%` нужно URL-кодировать. Для проверки сертификата используйте `sslmode=verify-full&sslrootcert=/path/to/certificate` с сертификатом из Supabase. [Настройка TLS](https://supabase.com/docs/guides/platform/ssl-enforcement).
3. Установите зависимости: `.venv/bin/python -m pip install -r requirements.txt`.
4. Запустите `.venv/bin/python -m backend.db init`. Команда применяет миграции из `supabase/migrations/` и заполняет пустую базу текущим датасетом.
5. Запустите `.venv/bin/python -m backend.db status`, затем `./run.sh`.

Строка подключения берётся из панели конкретного проекта: хост пула зависит от региона и проекта. `SUPABASE_URL`, publishable/anon key и service-role API key не заменяют PostgreSQL URL. `.env` исключён из Git, значение `DATABASE_URL` скрыто из `repr(Settings)`.

Подключение по умолчанию требует TLS, подготовленные запросы отключены для совместимости с Transaction pooler. Для локального PostgreSQL без TLS можно явно указать `sslmode=disable`. Проверки выполняются в отдельных транзакциях, соединения закрываются после операции.

## Схема данных

Миграция создаёт приватную схему `career_quest`. В Supabase Table Editor выберите её в списке схем.

| Таблица | Содержимое |
|---|---|
| `employees` | Профиль, руководитель, роль, грейд и карьерная цель |
| `skills`, `employee_skills` | Справочник и оценённые уровни навыков |
| `role_profiles`, `role_required_skills`, `role_critical_skills` | Требования и критичные навыки роли |
| `events` | Основные свойства мероприятия |
| `event_target_roles`, `event_target_grades` | Аудитория мероприятия |
| `event_gains`, `event_prerequisites`, `event_sessions` | Развиваемые навыки, входные требования, даты |
| `activity_history` | Участие, прогресс, оценки и дата завершения |
| `runtime_completions` | Порядок завершений после запуска приложения |
| `idempotency_receipts` | Хеш запроса и точный JSON-ответ для повторной отправки |
| `proficiency_scale` | Описания уровней 0–5 |
| `dataset_state` | Метаданные набора, версия и контрольная сумма источника |
| `schema_migrations` | Применённые миграции и их контрольные суммы |

Внешние ключи защищают связи сотрудников, навыков, ролей, мероприятий и истории. Ограничения проверяют диапазоны уровней, прогресса и оценок. `position` сохраняет порядок списков исходного датасета и результатов API. Эффективные навыки вычисляются существующей проекцией; оценённые уровни в `employee_skills` не перезаписываются после курса.

## Инициализация и перенос состояния

`init` блокирует конкурентную инициализацию. Если `dataset_state` уже заполнена, начальный датасет повторно не загружается. Если база пуста и `CAREER_QUEST_STATE_PATH` существует, сначала проверяются контрольная сумма исходных данных, содержимое снимка и сохранённые ответы; затем они переносятся в одной транзакции. При ошибке переноса данные не публикуются, локальный снимок сохраняется.

После первичной загрузки база является источником данных. Перезапуск не читает JSON/CSV и не применяет старый локальный снимок повторно. Для добавления данных используется `POST /datasets/upload?mode=append`; для полной замены — существующий режим `replace`, который также очищает сохранённые ответы и порядок runtime-завершений.

Новые миграции применяются командой `.venv/bin/python -m backend.db migrate`. Уже применённые файлы нельзя редактировать: контрольная сумма выявит изменение. `init` также выполняет миграции. При обычном старте API DDL не выполняется; если таблиц ещё нет, запуск подскажет команду `init`.

## Транзакции и доступ

Для каждого изменения backend блокирует единственную строку `dataset_state` через `SELECT ... FOR UPDATE`, читает актуальные данные, выполняет бизнес-проверки и сохраняет изменённые строки вместе с новой версией. Это предотвращает потерю изменений при нескольких workers. Чтения используют `REPEATABLE READ`, чтобы получить согласованный снимок всех таблиц. Повтор завершения с тем же ключом возвращает исходный ответ, не повышая версию.

При разрыве соединения во время подтверждения транзакции клиент может не знать, прошла ли запись. Повторяйте завершение с прежним `Idempotency-Key`; сохранённый ответ исключит двойное начисление. Для импорта сначала проверьте текущее состояние, поскольку импорт не использует этот ключ.

Таблицы имеют RLS без клиентских политик и находятся вне `public`; схема и таблицы не предоставляют доступ ролям `anon` и `authenticated`. Подключение backend должно выполняться владельцем таблиц, обычно `postgres` из Supabase Connect. Владелец обходит RLS, поэтому проверки HR/employee выполняются в FastAPI. Не добавляйте `career_quest` в Exposed schemas и не передавайте PostgreSQL пароль frontend. [Доступ к Data API](https://supabase.com/docs/guides/api/securing-your-api).

Текущий backend рассчитывает аналитику и рекомендации на снимке всего датасета. Запись обновляет только изменившиеся строки, но чтение снимка загружает все сущности. Это соответствует масштабу демо; для больших наборов потребуются SQL-фильтрация и отдельные агрегирующие запросы.

## Проверка

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Интеграционные проверки PostgreSQL запускаются при наличии `CAREER_QUEST_TEST_DATABASE_URL`. Используйте отдельную тестовую базу и роль с правом создания схем. Каждый тест работает в собственной схеме `cq_test_<uuid>` и удаляет только её после завершения. Покрываются официальный датасет, перезапуск, перенос локального состояния, замена набора, откат ошибок записи и одновременные завершения из разных экземпляров репозитория.
