# Контракт объяснений рекомендаций — шаг 4

Слой `backend/ai/` добавляет объяснения к **уже выбранным** рекомендациям. Он не выбирает мероприятия, не меняет допуск, порядок, ранги, оценки, факторы, навыки или готовность. Исходный результат копируется через `deepcopy`; добавляются только поля объяснений.

Детерминированные объяснения работают без сети, ключа и OpenAI SDK. Реализация использует стандартную библиотеку Python и не зависит от FastAPI, HTTP-моделей backend, базы данных или frontend. Движок рекомендаций не импортирует этот слой.

## Python API

```python
from backend.recommendation.engine import recommend
from backend.ai.explanations import enrich_recommendations

selected = recommend(
    employee,
    role_profiles,
    events,
    history,
    as_of="2026-10-01",
    top_n=3,
)

# Полностью локальный режим — значение по умолчанию.
explained = enrich_recommendations(
    selected,
    preferred_language="ru",
)

# Явно включённое необязательное обогащение через OpenAI.
# Ключ читается из OPENAI_API_KEY, а не из аргументов сотрудника.
enriched = enrich_recommendations(
    selected,
    preferred_language="kk",
    use_openai=True,
)
```

Полная сигнатура:

```python
enrich_recommendations(
    result,
    *,
    preferred_language="ru",
    use_openai=False,
    config=DEFAULT_EXPLANATION_CONFIG,
    environ=None,
    transport=None,
)
```

`result` — полный результат `recommend()`, содержащий выбранные рекомендации, симуляции, доказательства допуска, историю, сведения скоринга и диагностику отсутствия кандидатов. Функция не загружает данные и не восстанавливает рекомендации из одного `employee_id`.

Поддерживаются `kk`, `ru`, `en`. Неизвестный язык приводит к русскому объяснению с явным `language_fallback=True`. Выбор языка не меняет решения движка. Названия ролей, грейдов и идентификаторы навыков сохраняются как в исходных данных.

`environ=None` означает использование `os.environ`. Передача собственного отображения и функции `transport` нужна для тестов и адаптера; функции транспорта передаются `payload`, `api_key` и `timeout_seconds`. Значение `use_openai` должно быть именно `bool`.

Некорректный обязательный результат движка — например, несовпадающие количества, повторяющиеся ID, нарушенные ранги или противоречивые изменения дефицита — вызывает `RecommendationInputError` с кодом `invalid_explanation_evidence`. Некорректный `use_openai` вызывает `invalid_explanation_option`. Это ошибки входного контракта; для них невозможно обещать корректное объяснение. Ошибки необязательного провайдера обрабатываются отдельно через fallback.

## Дополнительные поля результата

Каждая выбранная рекомендация получает поле `explanation`:

| Поле | Смысл |
|---|---|
| `language` | Фактически использованный язык: `kk`, `ru` или `en` |
| `source` | `deterministic` либо `openai` |
| `text` | Соединённые предложения объяснения |
| `facts` | Упорядоченные факты из доказательств движка |
| `segments` | Упорядоченные предложения с соответствующими `fact_id` |

Каждый факт содержит `fact_id`, `code`, `values`, `evidence_paths`. Последнее поле хранит пути к исходным данным внутри результата, например `/recommendations/0/simulation/readiness_after`. Каждый сегмент содержит `fact_id` и `text`.

Объяснение использует существующие сведения о цели, полезных изменениях навыков, обычных и критических дефицитах, закрытии требований, готовности, основании допуска по роли, текущем грейде, доступности, полезном приросте, агрегатах истории и обратной связи. При оценочном восстановлении навыков добавляется соответствующее пояснение. Готовность описывается как покрытие требований цели, без гарантии повышения.

Объясняются изменения, полезные для целевых требований; остальные изменения навыков остаются доступны в исходной симуляции. Проценты готовности отображаются с двумя знаками после запятой, изменение — в процентных пунктах; сигналы истории — с тремя знаками. Исходные числовые поля не округляются и не заменяются.

На верхнем уровне добавляются:

- `explanation_summary` — объяснение состояния результата в том же формате. Оно всегда детерминированное.
- `explanation_meta` — сведения о языке и необязательном провайдере.

Пример метаданных при локальном выполнении:

```json
{
  "requested_language": "ru",
  "language": "ru",
  "language_fallback": false,
  "openai_requested": false,
  "provider_status": "disabled"
}
```

Если рекомендаций нет, summary сохраняет различия между `no_eligible_recommendations`, `no_next_grade`, `target_satisfied` и `invalid_target_requirements`. Для доступной диагностики показываются причины отказов и непокрытые целевые дефициты. Счётчики причин могут пересекаться: одно мероприятие может иметь несколько причин отказа. Диагностика непокрытых дефицитов относится к полезному приросту из текущего состояния даже при игнорировании условий допуска.

## Что делает OpenAI

Это **ограниченный выбор формулировок**, а не свободная генерация объяснения. Для каждого уже установленного факта локально подготовлены два варианта на нужном языке:

- `direct` — прямое изложение;
- `coaching` — формулировка, предлагающая рассмотреть тот же факт.

Модель получает ID выбранных мероприятий и упорядоченные факты с двумя готовыми фразами. В ответе разрешены только язык, ID мероприятий, ID фактов и выбранные варианты. Произвольный текст, новые числа, навыки, утверждения, мероприятия или поля не принимаются.

Один запрос охватывает весь выбранный набор. Используются Responses API, `store=False`, пустой список `tools` и строгий `text.format` с JSON Schema. После ответа локально проверяются:

1. Поддерживаемая структура REST-ответа: завершённый ответ с одним завершённым сообщением assistant и одним блоком `output_text`.
2. Корректный JSON без дублирующихся ключей и неподдерживаемых полей.
3. Точное совпадение языка, количества и порядка мероприятий.
4. Точное совпадение количества, порядка и идентификаторов всех фактов каждого мероприятия.
5. Принадлежность каждого варианта множеству `direct`, `coaching`.

Текст после успешной проверки **снова собирается локально** из разрешённых шаблонов. `source="openai"` означает, что модель выбрала варианты; это не означает, что модель написала произвольный текст. Даже если модель выбирает везде `direct`, источник помечается как `openai`, а факты остаются прежними.

Если хотя бы одна рекомендация или один факт не проходит проверку, отклоняется **весь ответ провайдера**. Все рекомендации получают исходные детерминированные объяснения. Частичное смешивание успешных и неуспешных AI-результатов не применяется.

## Конфигурация

Параметры представлены неизменяемым `ExplanationConfig` в `backend/ai/config.py`.

| Параметр | По умолчанию | Ограничения / настройка |
|---|---:|---|
| `model` | `gpt-4.1-mini` | Непустой идентификатор без пробельных символов, максимум 200 символов |
| `timeout_seconds` | `3.0` | Конечное число больше 0 и не больше 10 |
| `max_output_tokens` | `4096` | Положительное целое число |
| `max_payload_bytes` | `65536` | Положительное целое число; проверяется UTF-8 размер запроса |

При `use_openai=True` учитываются переменные окружения:

| Переменная | Значение |
|---|---|
| `OPENAI_API_KEY` | Ключ для явно включённого запроса; отсутствие или пустая строка приводит к fallback |
| `OPENAI_MODEL` | Непустое значение переопределяет `config.model` |
| `OPENAI_TIMEOUT_SECONDS` | Непустое значение преобразуется в число и переопределяет тайм-аут |

`.env` автоматически не загружается: окружение подготавливает вызывающая сторона. Ключ не включается в результат, тексты объяснений, JSON payload или сообщения ошибок. В транспорте он используется только в заголовке `Authorization`.

## Состояния провайдера

`explanation_meta.provider_status` описывает исход необязательного обогащения, а не статус карьерной рекомендации:

| Значение | Значение для вызывающей стороны |
|---|---|
| `disabled` | OpenAI не запрошен; выполнено локальное объяснение |
| `no_recommendations` | OpenAI запрошен, но список рекомендаций пуст; сеть не используется |
| `missing_api_key` | Нет непустого строкового ключа; сеть не используется |
| `invalid_config` | Некорректны отображение окружения, конфигурация или её переопределения |
| `payload_too_large` | Подготовленный запрос превышает лимит; сеть не используется |
| `invalid_output` | Невозможна безопасная сериализация запроса либо ответ/JSON повреждён, неполон, содержит refusal или неподдерживаемый REST output |
| `unsupported_output` | JSON разобран, но содержит недопустимые поля/значения, другой язык, чужие ID, пропуски, дубликаты или изменённый порядок |
| `timeout` | Истекло время ожидания либо транспорт сообщил тайм-аут |
| `api_error` | Ошибка API/сети, другая ошибка провайдера или занятый единственный provider slot |
| `used` | Весь ответ проверен, локально применены выбранные формулировки |

Во всех состояниях, кроме `used`, рекомендации сохраняют детерминированные объяснения. Отказ AI не изменяет исходные ранги, оценки, данные симуляции или диагностику.

## Время ожидания и транспорт

Транспорт выполняет один POST на фиксированный `https://api.openai.com/v1/responses`. Повторных попыток нет. Перенаправления отключены, чтобы заголовок авторизации не передавался другому адресу. Ответ ограничен 256 КиБ. Тела HTTP-ошибок не читаются и не возвращаются вызывающей стороне. На уровне транспорта доступны только безопасные коды `timeout`, `api_error`, `invalid_response`; контроллер преобразует последний в `invalid_output`.

Параметр `timeout_seconds` применяется к сетевым операциям и ожиданию ответа фонового daemon-потока. Даже если пользовательский транспорт или DNS не соблюдает сетевой тайм-аут, вызывающая функция прекращает ожидание и возвращает fallback. Локальная подготовка и окончательная сборка объяснения находятся вне этого ожидания.

В одном процессе одновременно допускается только один provider worker. Очереди нет: конкурентный вызов сразу получает fallback с `api_error`. Уже запущенный зависший поток принудительно не завершается; slot освобождается при его фактическом завершении. Это ограничивает число фоновых запросов, но может временно отключать AI-обогащение для остальных вызовов процесса. Детерминированные объяснения продолжают работать.

## Границы данных и проверка

В провайдерский payload включаются только выбранные ID мероприятий и готовые варианты фраз по фактам. Не включаются employee ID, полная анкета, полный каталог, отдельные записи истории, ID участий, подробный `record_evidence`, заметки backend и свободный текст отзывов. Агрегаты истории, роли, навыки и значения симуляции могут входить в фразы, поскольку они объясняют конкретную рекомендацию. Исходный результат движка возвращается с прежними полями; слой объяснений не является фильтром всех данных для будущего публичного API.

Тесты используют подменённый транспорт и моки `urllib`. Они проверяют три языка, отсутствие ключа, успешный выбор формулировок, ошибку API, тайм-аут, некорректный JSON, неподдерживаемые утверждения, перестановки и пропуски, полный fallback, неизменность результата движка, ограничение payload и безопасный транспорт.

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests/recommendation -v
```

**Живой вызов OpenAI API на этом шаге не проверялся.** Ключ и платные запросы для локальной работы и тестов не нужны. Успешные тестовые ответы проверяют контракт адаптера, но не подтверждают доступ конкретного аккаунта к модели, сетевую доступность или реальную задержку провайдера.

## Официальные источники API

Формат `text.format`, строгая схема и особенности Structured Outputs описаны в [руководстве OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Одной схемы недостаточно для доказательства фактической корректности; поэтому локальная проверка фиксирует весь набор фактов и допустимые формулировки.

Параметры Responses API и формат результата сверяются с [официальным справочником создания ответа](https://developers.openai.com/api/reference/python/resources/responses/methods/create). Сам адаптер обращается к REST endpoint стандартной библиотекой Python; установка SDK для этого не требуется.
