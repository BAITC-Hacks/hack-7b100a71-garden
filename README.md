# Career Quest

Career Quest для HackAlem AI / Halyk Bank: карьерная цель сотрудника → дефициты навыков → объяснимые Top 1–3 активности → завершение → обновлённый прогресс. React + FastAPI + детерминированный Python-движок. Отдельный сервер БД и OpenAI-ключ для запуска не нужны.

Backend Bekarys подключён к движку Zhanibek: карьерная цель, ранжирование, readiness и объяснения уже доступны через API. React frontend Adilet интегрирован с реальным API в `frontend/`. Инструкции запуска интерфейса находятся в [frontend/README.md](frontend/README.md), точный HTTP-контракт — в [FRONTEND_API_CONTRACT.md](docs/FRONTEND_API_CONTRACT.md), результаты проверки — в [отчёте Phase 2](docs/integration-phase2-audit.md).

## Быстрый запуск демо — два терминала

Полная интегрированная версия находится в ветке **`codex/team-integration`**.
Команды ниже выполняются из её корня. Нужны **Python 3.11+** и **Node.js 22.12+**
(вместе с npm). Отдельная установка pnpm не обязательна: команды используют npx.
При первой установке зависимостей нужен интернет.

**Терминал 1 — backend:**

```bash
CAREER_QUEST_AUTH_DISABLED=true OPENAI_API_KEY= ./run.sh
```

Скрипт создаёт `.venv`, устанавливает зависимости и запускает API на
**http://127.0.0.1:8000**. Оставьте терминал открытым.
Проверка запуска: [health](http://127.0.0.1:8000/health) должен вернуть `status: ok`.
[Swagger](http://127.0.0.1:8000/docs) — документация API.

**Терминал 2 — frontend:**

```bash
cd frontend
npx --yes pnpm@11.25.0 install --frozen-lockfile
VITE_API_MODE=real VITE_API_BASE_URL=http://127.0.0.1:8000 npx --yes pnpm@11.25.0 dev --port 5173 --strictPort
```

Откройте **http://127.0.0.1:5173**. Frontend обращается к настоящему FastAPI.
Если pnpm уже установлен, вместо `npx --yes pnpm@11.25.0` можно использовать `pnpm`.
Остановка каждого сервера: `Ctrl+C` в соответствующем терминале.

**Что ввести на экране входа в этом локальном деморежиме:**

| Поле | Для показа HR | Для показа сотрудника |
|---|---|---|
| Workspace | `HR` | `Employee` |
| Employee ID | не требуется | `E0001` или другой ID из датасета |
| Access token | `demo-local` | `demo-local` |

`demo-local` — произвольная непустая строка для формы, **не секрет и не действующий
токен защищённого режима**. В команде выше backend-авторизация явно отключена:
сервер разрешает HR-доступ. Этот способ предназначен только для локального показа
синтетического датасета. Для проверки настоящего разграничения ролей используйте
следующий раздел. После перезагрузки вкладки нужно снова войти.

Пустой `OPENAI_API_KEY` в команде обеспечивает запуск без внешнего LLM:
рекомендации, оценки и объяснения kk/ru/en работают детерминированно. Для
необязательного OpenAI-обогащения задайте собственный ключ на backend и уберите
`OPENAI_API_KEY=` из команды. Ключ никогда не передаётся frontend.

## Вход с настоящим разграничением employee / HR

В корневом локальном `.env` задайте свои значения (не коммитьте файл):

```dotenv
CAREER_QUEST_AUTH_DISABLED=false
HR_API_TOKEN=your-own-hr-token
EMPLOYEE_TOKENS_JSON={"your-own-e0001-token":"E0001","your-own-e0004-token":"E0004"}
```

Запустите backend командой `CAREER_QUEST_AUTH_DISABLED=false ./run.sh`.
В форме входа HR использует значение `HR_API_TOKEN`; сотрудник — свой ID и
соответствующий токен из `EMPLOYEE_TOKENS_JSON`. Здесь строки `your-own-…` нужно
заменить собственными токенами. Выбор Workspace не расширяет серверные права.
Employee видит только себя и не запрашивает HR directory. HR может открывать
всех сотрудников, аналитику и импорт. Полноценного SSO/login-сервера в MVP нет.

## Показ жюри за 3–5 минут

Сценарий ниже относится к исходному датасету без уже выполненных demo-completion.

1. Войти как HR и открыть **E0001**: Backend Engineer → Middle, readiness **58.97%**,
   EV_005 на первом месте. Раскрыть **Why this?** и **Score, factors and evidence**.
2. Нажать **Complete activity** у EV_005. Показать receipt и обновление:
   API Design **2 → 3**, System Design **1 → 2**, readiness **66.67%**.
   EV_005 исчезает, EV_036 остаётся.
3. Открыть **E0004**: переход в Product Manager / Middle, EV_026, `target_role`.
   После completion readiness **42.11% → 52.63%**.
4. **E0006** — Lead без следующего грейда; **E0018** — нет подходящих активностей.
   Это корректные результаты, не ошибки.
5. **HR overview**: дефициты текущей роли, участие, полнота рекомендаций.
   В **Validate & upload dataset** загрузить файл жюри → **Validate files** →
   проверить counts → **Upload validated files**. Новый сотрудник появится в selector.

Для нового чистого показа, сохранив предыдущие результаты, остановите backend и
запустите его с новым отдельным файлом состояния:

```bash
CAREER_QUEST_AUTH_DISABLED=true OPENAI_API_KEY= CAREER_QUEST_STATE_PATH=".runtime/demo-$(date +%Y%m%d-%H%M%S).json" ./run.sh
```

Запомните путь: для продолжения этого же показа после restart используйте **тот же
файл**, а не новую дату. Основной `.runtime/state.json` при этом не удаляется.

## Если запуск не удался

- `python`/`node` не найден: установите указанные выше версии; проверьте `python3 --version` и `node --version`.
- Порт 8000/5173 занят: остановите предыдущий сервер. `--strictPort` не даст Vite
  молча переключиться на 5174, который не входит в стандартный CORS.
- `Backend unavailable`: проверьте открытый терминал backend, `/health` и адрес API.
- `401`/`403`: сверяйте выбранный режим авторизации и токен. `demo-local` работает
  только при `CAREER_QUEST_AUTH_DISABLED=true`.
- Уже показаны улучшенные навыки: сохранён предыдущий completion; используйте отдельный
  файл состояния для нового показа. Это работа persistence, а не ошибка расчёта.
- Ошибка отсутствующего датасета: нужны все четыре файла в `data/career_quest_dataset/`
  или правильный `CAREER_QUEST_DATA_DIR`. Они включены в integration-ветку.

## Основные API

Успех имеет форму `{ "data": ... }`, списки добавляют `meta` с пагинацией, датой и версией набора. Ошибки имеют форму `{ "error": { "code": "...", "message": "...", "details": [] } }`.

| Маршрут | Назначение |
|---|---|
| `GET /health` | Состояние, дата и размеры набора |
| `GET /employees` | Список сотрудников для HR; фильтры и пагинация |
| `GET /employees/{id}` | Исходный профиль, требования текущей роли и эффективные навыки |
| `GET /employees/{id}/history` | История участия |
| `GET /employees/{id}/recommendations` | Результат подключённого движка |
| `GET /events`, `GET /events/{id}` | Каталог мероприятий |
| `GET /skills`, `GET /skills/{id}` | Справочник навыков |
| `GET /role-profiles` | Требования по ролям и грейдам |
| `POST /activities/{event_id}/complete` | Завершение с защитой от повторной обработки |
| `GET /hr/analytics` | Дефициты навыков и агрегаты участия |
| `POST /datasets/validate` | Проверка файлов без изменения состояния |
| `POST /datasets/upload` | Атомарное добавление или полная замена данных |

Запрос завершения содержит `employee_id`, необязательные `record_id`, `score` и `feedback_rating`. Обязателен заголовок `Idempotency-Key`: повтор того же запроса возвращает сохранённый ответ без повторного начисления. При наличии активной записи она переходит в `completed`; дата зачисления сохраняется, новая дата завершения записывается в `completed_on`. Обязательное обучение можно завершить только по существующему назначению, без начисления игровых наград.

## Как устроена «БД» и сохранение данных

Для этого MVP используется **персистентное файловое хранилище**, а не SQL-СУБД.
PostgreSQL, SQLite, Redis, Docker и миграции устанавливать не нужно.

| Что | Где |
|---|---|
| Официальные исходные профили, навыки, события и история | `data/career_quest_dataset/*.json` и `activity_history.csv` |
| Активный рабочий набор во время работы | Repository в памяти backend |
| Завершения, импорт, runtime chronology, версия и idempotency receipts | `.runtime/state.json` по умолчанию |
| Рекомендации и объяснения | Вычисляются по текущей версии, кешируются в процессе |

Официальные файлы находятся в `data/career_quest_dataset/`: 200 сотрудников, 60 навыков, 32 профиля роли и грейда, 40 мероприятий и 2 743 записи истории. Исходные файлы сохранены без изменений; датой демо служит `meta.as_of_date`, для стартового набора это `2026-10-01`.

`employee.skills` остаётся результатом последней оценки. `get_effective_skills()` единожды учитывает завершённые после неё активности. Курс не может уменьшить уже более высокий уровень навыка. Описание неоднозначностей исходной истории и принятых трактовок находится в [DATASET_NOTES.md](docs/DATASET_NOTES.md).

Завершения, импортированные профили и ответы на повторные запросы сохраняются в `.runtime/state.json`. Запись атомарная: при ошибке сохранения изменения не применяются. Состояние восстанавливается после перезапуска и связано с исходным датасетом по контрольной сумме. Для чистого демо остановите сервер и переместите этот файл в резервную копию.

Приложение работает с **одним worker**; потоки запросов сериализуют изменения общим замком. Для хранения только в памяти задайте пустое значение `CAREER_QUEST_STATE_PATH`. Остальные настройки перечислены в `.env.example`. Если переносите demo на hosting,
путь состояния должен находиться на записываемом постоянном диске/volume;
эфемерная файловая система контейнера не сохраняет данные между пересозданиями.
Исходный датасет тоже нужен при каждом запуске. Для локального ноутбука обычного
каталога `.runtime/` достаточно.

## Импорт данных жюри

Отправляйте multipart-файлы с полями `employees_file`, `activity_history_file`, `events_file`, `skills_file`.

- `mode=append` по умолчанию добавляет новые профили и/или записи истории. Можно прислать один файл; ссылки проверяются по всему активному набору. Повторные ID отклоняются. Ранее импортированные данные и завершения сохраняются.
- `mode=replace` требует все четыре файла и заменяет рабочий набор целиком. Старые ответы идемпотентности и сведения о runtime-завершениях сбрасываются.

JSON сохраняет официальные оболочки с `meta`; метаданные должны совпадать. CSV разбирается настоящим CSV-парсером, включая переставленные столбцы и значения в кавычках. Проверяются типы, уровни навыков, даты, уникальность и ссылки. Невалидный импорт не меняет состояние. Лимит общего содержимого файлов по умолчанию — 10 MiB.

## Подключение рекомендаций

Движок подключён по умолчанию. Backend использует типизированный адаптер, изолированный снимок данных, общую реконструкцию навыков, таймаут и кеш по версии данных. Завершение или импорт делает прежние рекомендации устаревшими. OpenAI используется только для необязательного обогащения объяснений; без ключа работают детерминированные объяснения. Ранжирование и оценки от OpenAI не зависят.

HR-дефициты относятся к требованиям **текущей роли и грейда**. Показатель сотрудников без следующего шага получает точную сводку через необязательный быстрый метод `provider.coverage(view)` либо показывает только уже рассчитанные рекомендации вместе с количеством ещё не оценённых сотрудников. Отсутствующие результаты не выдаются за ноль. Открытие HR-экрана не запускает массовую генерацию AI-объяснений.

## Проверка

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тесты проверяют официальный датасет, повреждённые JSON/CSV и ссылки, новые профили, транзакционный импорт, границы доступа, рост навыков, порядок завершений, повторные и конкурентные запросы, восстановление состояния и ошибки подключаемого движка. Основные сценарии используют небольшие синтетические наборы с произвольными ID.
